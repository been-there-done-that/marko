Budgets come from PLAN.md §10. Numbers are from one release build (`cargo build --release`,
thin LTO, stripped) on the Linux development laptop (Wayland session, 16 logical CPUs), with
`fixtures/basic.md` open. Each row says what the number leaves out.

## Image memory

Decoding keeps at most 32 MB of decoded RGBA at once, and a picture whose decoded form would
exceed 64 MB is refused from its header before the decoder allocates. A tall image is scaled to
the cache budget instead of being decoded at full size and then rejected. JPEGs are decoded at a
1/8, 1/4 or 1/2 DCT scale when they are larger than the reading column, so a large photo never
allocates its full-resolution buffer. Only the active tab's window around its scroll position is
decoded, at most four decodes are in flight, and they run one at a time across the local and web
workers. The background is decoded at 2560 px wide. These bound the transient decode peak; they
do not change the RSS number above, which was taken with one small document and no large image on
screen.

The 32 MB cache counts decoded RGBA, not total memory: `rune` keeps a premultiplied CPU mip chain
and a GPU texture for each cached picture, so budget about 2.5× the RGBA bytes per image.

### Image-heavy measurement

`fixtures/image-heavy.md` opens six 4000 × 3000 pictures (four PNG, two JPEG). The pictures are
generated by `python3 scripts/make-image-fixtures.py`; they are solid colours to keep the files
tiny (588 KB total), but each decoded PNG frame is 48 MB. The run used a fresh
`XDG_CONFIG_HOME`, so no session or background image was loaded:

```
XDG_CONFIG_HOME=<fresh dir> target/release/marko fixtures/image-heavy.md
```

After 20 s, `/proc/<pid>/status` read `VmHWM 273,272 kB` (266.9 MB) and `VmRSS 148,432 kB`
(144.9 MB). The same build with `fixtures/hello.md` (no pictures) read 49,884 kB (48.7 MB) for
both. The lazy window queued only the first two PNGs, and RSS was flat from 6 s to 20 s, so the
stable window is not re-decoding. The peak is the full-resolution PNG frame plus the resized
picture and `rune`'s mip chain; a streaming PNG decoder is the next win (see `docs/pending.md`).

## Cold start

Not measured. Rune's launch timing (`crates/rune/src/tooling/perf_warn/launch.rs`) is compiled
only under `cfg(debug_assertions)` and reports only when the first frame exceeds its warning
threshold, so a release build prints no timing. There is no `RUNE_FLIGHT` variable; the
`flight` module in Rune is for animation flights, not startup. Measuring cold start needs
either a debug build or a timestamp taken in the app's `on_ready` against process start, which
this pass did not add.

## How the numbers were taken

- Binary: `ls -l` on the release binary in the shared target directory.
- RSS: start the release binary with `fixtures/basic.md` in the background, wait 3 s, read
  `VmRSS` from `/proc/<pid>/status`.
- Idle CPU: read `utime + stime` (fields 14 and 15 of `/proc/<pid>/stat`) at the start and
  after 20 s with no input; the difference is the idle tick count. The process was then stopped.
- Each number is one run, not a median of paired runs. Treat them as first readings.
